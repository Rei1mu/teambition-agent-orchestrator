## 1. 截图能力（默认 BitBlt 后台截图）

**入口**：窗口左侧「通用能力 → 截图」+ CLI `tba shot`

**默认走 BitBlt 后台截，不激活、不置顶、不抢焦点**（这是硬要求，之前用整屏截图 + SetForegroundWindow 的做法作废）：

```
GetWindowDC(hwnd) → CreateCompatibleDC/Bitmap → BitBlt(SRCCOPY) → GetDIBits → 写 PNG
```

**兜底**：BitBlt 结果全黑或失败时，自动切 `PrintWindow(hwnd, hdc, 0)`（WM_PRINT，窗口被遮挡/最小化也能正确渲染）。可用 `--method bitblt|print|auto` 强制指定，默认 `auto`（先 BitBlt，黑了再 PrintWindow）。

**参数**：

| 参数 | 说明 |
|---|---|
| `--title <子串>` | 按窗口标题找窗口 |
| `--pid <pid>` | 按进程找窗口 |
| `--out <路径>` | 输出文件，缺省 `data/shots/<时间戳>.png` |
| `--method` | `auto`（缺省）/ `bitblt` / `print` |
| `--open` | 截完用系统默认程序打开 |

缺省截 **tba 自己的窗口**。截图落 `data/shots/`，只回一行 `OK <路径>`，不把图像塞进 agent 上下文。

**实现**：`src/shot.rs`，纯 Win32 FFI（GetWindowDC/BitBlt/GetDIBits/PrintWindow），手写 PNG 编码（zlib 存证 + CRC32），不引第三方 crate。

## 4. 无痛重载

**核心规则：编译完才 kill，任何一步失败都不影响正在跑的应用。**

```
① 编译     cargo build --release（产物被锁时先把运行的产物改名让开，进程名不变，用户无感）
② 校验     新产物存在、大小正常；失败 → 还原改名，旧应用原封不动
③ 杀旧     按 pid 杀，永不包括调用方；覆盖 tba / tb_test 两个进程名
④ 覆盖     新产物写到运行位置（直跑模式即产物本身，copy 模式写副本）
⑤ 运行     启动新 exe，清理 .old
```

- 只有 ① 成功才进 ③，编译失败时旧应用继续跑，窗口不闪、不丢
- `--mode rename`（缺省）直跑；`--mode copy` 保留副本模式，两条路都满足「先编译后切换」
- 按钮文案改「无痛重载」，面板里把上面 5 步画出来，让 agent 和人看的节奏一致
- 退出码仍是唯一真值：`OK <pid>` / `ERR <step>:<msg>`

## 附：实现前必须知道的服务端约束（2026-10-24 实测）

这些是对接真实 Teambition 时挖出来的硬约束，**实现前先读，否则会重复撞墙**。

### 概念对应

- TBHub 的「阶段」= Teambition 的**工作流状态（tfs）**，不是任务列表。任务对象同时带 `stageId`（任务列表 id）和 `tfsId`（工作流状态 id），两者不是一回事。
- TQL 查某阶段的任务用 `taskflowstatusId = '<tfs_id>'`；用 `stageId` 查会返回 0 条**但仍报成功**，极阴。
- 工具映射见 `data/config.toml` 的 `[tool_overrides]`（`tools.rs` 的模糊匹配在真实工具集下错得厉害，也该修）。

### 建阶段（`project.taskflow-update` 的 `tfsJson`）

- `kind` 枚举**只有 `start` / `end`**，没有中间态；不传默认变 `start`。
- **`start` 必须恰好 1 个**：删到 0 个报 `At least 1 kind of start`，建第 2 个报 `ShouldOnlyOneStartStatus`。`end` 个数不限。
- `upsert` **只能插入不能更新**：名字已存在报 `X exists`，传 `id` 也没用。改 `kind` 只能「`remove` + `upsert` 放同一次调用」。
- **多条 `upsert` 只生效最后一条**，建多个状态必须分多次调用。
- `pos` 更新会被拒，看板列序调不了。

### 建/移任务

- `task.create` 的 `taskflowstatusId` / `tfsName` **必须是 `kind=start` 的状态**，否则报 `taskflowstatus should be start kind`。
- 因此只有一个状态能直接收新任务 → **「待处理」= `start`**；「进行中」= `unset`；「已解决」/「关闭」= `end`。
  （2026-10-24 后续修正：`kind` 是三态 `start/unset/end`，不是只有两态；「项目skill」阶段已废弃，skill 改为任务类型 `sfcId`。）
- 往 `end` 阶段放任务的唯一办法：先建在 `start` 阶段，再用 `task.update-status` 按 `tfsName` 挪过去。**`tba skill-push` 必须改成这个两步流程。**
- `task.create` 的 schema 是 `additionalProperties: false`，传 `stageId` 会被整体拒掉；只能用 `content` / `note` / `projectId` / `tfsName` / `taskflowstatusId`。

### tba 代码对接层（2026-10-24 已修完并双向实测通过）

修之前 `tba skills` / `tba tasks` 对真实服务能跑但返回空。以下全部改完，`cargo check` 零警告：

| 位置 | 原问题 | 修法 |
|---|---|---|
| `tools.rs parse_task` | `stage_id` 先读 `stageId`（真实 API 里是任务列表 id），阶段过滤把任务全筛掉 | 优先 `tfsId` / `taskflowstatusId`，`stageId` 只兜底 |
| `ops.rs list_tasks` | 第一个候选 TQL 用 `stageId`，0 条还当成功返回 | `taskflowstatusId` 优先；前两条算精确筛选（空也认），后三条粗筛只有非空才算数 |
| `ops.rs create_task` | 传 `stageId`，而 `task.create` 是 `additionalProperties:false`，整体被拒 | 改用 `taskflowstatusId` / `tfsName` + `content` + `note`；并加「先建再挪」退路 |
| `ops.rs move_task` | 用错工具和参数 | 签名改收 `&StageInfo`；多候选工具回退（真实 API `task.update-status`，mock `task.move`） |
| `ops.rs ensure_stages` | `create_stage` 传 `name/title`，服务端不认（`taskflow-update` 的 `name` 是「重命名工作流」） | 按工具名分派：`taskflow-update` 走 `tfsJson` upsert，mock 走 `name` |
| `tools.rs` 角色规则 | 模糊匹配错得厉害（`create_task`→上传工具、`get_project`→smartgroup-get、`list_stages`→plan.status-query） | 加 30 个噪声词表接进打分函数，所有规则补 `project` 加分 |

**「先建再挪」退路**：`task.create` 只能建在 `kind=start` 的状态里，而一个任务流只有一个 start。所以 `create_task` 直接建失败时，先建（落默认 start 态）再 `move_task` 挪到目标阶段。
（2026-10-24 后续修正：skill 不再是「项目skill」阶段，而是任务类型 `sfcId=skill`，建在「已解决」阶段，靠上面这条退路落地。）

**验证**：真实项目上 `tba skills` / `tba tasks` / `tba prompt` / `tba claim` / `tba done` / `tba skill-push` 全通；mock 上另测了 `init` 幂等、`switch` 开关、无 overrides 时的角色自动识别。
